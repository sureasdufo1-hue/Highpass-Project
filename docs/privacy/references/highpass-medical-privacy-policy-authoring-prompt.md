# 하이패스 다음 문서 선정 및 작성 프롬프트

작성일: 2026-09-06  
기준 문서: 「하이패스 OpenAI Privacy Filter 의료개인정보 보호 기능 구현계획서」 v1.0  
다음 작성 대상: **「하이패스 의료개인정보 처리정책·판정기준 명세서」 v1.0**

## 이 문서를 먼저 작성하는 이유

구현계획서에는 처리 구조, API 예시, 작업 상태, 개발 일정과 평가 목표가 정리되어 있다. 다음에는 그 구조가 적용할 **판정의 기준**을 구체화하는 것이 유용하다.

예를 들어 “목적에 불필요한 정보를 제거한다”, “날짜는 목적에 따라 처리한다”, “임상 표현과 충돌하면 검토한다”라는 원칙을 실제 입력에 적용하려면, 어떤 조건에서 무엇을 삭제·대체·유지하고 어떤 증거가 있어야 검토를 마칠 수 있는지 정해야 한다. 이 기준이 있어야 개발 코드, 한국어 평가 데이터의 정답, 검토자의 판단이 일치한다.

| 작성 순서 | 문서 | 다음 작업에 제공할 기준 |
| --- | --- | --- |
| 지금 | 의료개인정보 처리정책·판정기준 명세서 | 목적별 조치, 예외, 판정 예시, 검토·반출 조건 |
| 다음 | 상세설계서 및 API·DB 계약 명세서 | 정책을 실제 저장소의 모듈·필드·상태 전이에 연결 |
| 이어서 | 평가 데이터셋·시험 명세서 | 확정한 판정 기준으로 600건 정답과 시험 절차 구성 |

저장소 조사와 환경 확인은 기존 PF-0 계획대로 진행할 수 있다. 이 문서는 정책 엔진 구현과 평가 정답 확정에 앞서 사용할 기준이며, 기존 일정을 새 문서 작업만큼 무조건 연장하라는 뜻은 아니다.

## 사용 방법

아래 “작성 프롬프트 시작”부터 끝까지 복사하여 사용한다. 구현계획서 v1.0을 함께 제공하면 가장 정확하다. 이 파일은 다음 문서를 만들기 위한 프롬프트이며, 정책 승인 완료나 구현 완료를 의미하지 않는다.

## 작성 프롬프트 시작

당신은 의료데이터 처리 정책 설계자이자 소프트웨어 요구사항·평가 기준 작성자다.

첨부된 **「하이패스 OpenAI Privacy Filter 의료개인정보 보호 기능 구현계획서」 v1.0**을 기준으로, 다음 문서를 한국어 Markdown으로 완성하라.

**문서 제목: 「하이패스 의료개인정보 처리정책·판정기준 명세서」 v1.0**

개발자와 평가 데이터 작성자, A병원 검토자가 동일한 입력에 대해 일관된 판단을 할 수 있도록, 처리 대상·목적·변환 규칙·충돌 해결·정답 예시·반출 조건을 명세하라. 목차나 작성 요령만 제시하지 말고, 규칙과 예시가 채워진 실제 문서 초안을 작성하라.

### 1. 입력 자료와 작성 원칙

다음 자료를 순서대로 대조하라.

1. 이 대화에서 사용자가 명시한 최신 결정.
2. 첨부된 구현계획서 v1.0. 특히 4.1 목적별 정책, 4.2 텍스트 처리, 4장의 DICOM 처리, 5장의 API·상태, 6장의 평가·시험 사례.
3. 제공된 경우 기존 설계 프롬프트, 저장소의 실제 정책·인가 계약, 조직별 식별자 설정.
4. 모델·DICOM·법률의 외부 사실 확인에 필요한 공식 1차 자료.

구현계획서의 제안을 이미 구현·승인된 사실로 표현하지 말라. 문서의 각 결정은 다음 중 하나로 구별하라.

- **기준 계획의 결정:** 구현계획서와 일치하는 설계 기준. 코드 존재나 기관 승인까지 증명하지는 않는다.
- **이 명세서의 제안:** 아직 결정되지 않은 항목에 이번 문서가 제안한 값.
- **확인 필요:** 자료가 없거나 실제 환경·기관 판단이 필요한 항목.

기준 계획을 바꿔야 하면 원래 결정, 변경 제안, 이유, 영향받는 정책·시험을 변경 제안 표에 적어라. 기존 목적 enum·상태·평가 목표를 조용히 바꾸지 말라.

자료가 부족해도 안전한 제안값과 확인 항목을 분리하여 문서 초안을 완성하라. 질문 목록만 남기고 중단하지 말라. 단, 근거·수신처·필수 처리 조건이 미확인인 작업을 승인 가능 상태로 표시하지 말라. 실제 저장소나 첨부 문서를 읽지 못했다면 그 범위를 문서 첫머리에 적고, 읽었다고 주장하지 말라.

### 2. 유지할 프로젝트 전제

다음은 기준 계획의 전제다. 실제 구축 여부와 구분하여 유지하라.

- Highpass는 A병원의 원본 PACS/DICOM을 보존하고, B병원이 허가된 DICOMweb 조회와 선택적 편입을 수행하는 프로젝트다.
- 개인정보 추론·원문 비교·가명 매핑은 A병원 Edge 신뢰 영역 안에서 수행한다.
- 중앙 제어 서버에는 원문 판독문, 원본 DICOM, 탐지된 개인정보 원문을 지속 저장하지 않는다.
- B병원 일반 Viewer 사용자에게 A병원의 원문 비교·개인정보 검토 권한을 부여하지 않는다.
- 첫 대상은 UTF-8 텍스트 판독문·의뢰서다. Privacy Filter와 한국어·기관별 규칙의 탐지를 결합하고 서버 정책이 조치를 결정한다.
- 진료 공유는 기존 인증·동의·환자 매칭 경로를 사용한다. 기존 진료 경로에서 필요한 식별정보를 무조건 가려 환자를 잘못 연결하지 않는다.
- 새 비진료 반출 API의 목적은 `RESEARCH / TEACHING / DEMO / AI_LOCAL`이다. 이 enum에 `CLINICAL`을 추가하여 진료 경로로 우회하지 않는다.
- `research-v1`은 `text-research-v1`과 `dicom-research-v1`을 연결하는 상위 정책 묶음이다. `text-demo-v1`은 텍스트 미리보기 프로파일이다. 서버가 등록된 목적·형식에 맞춰 선택한다.
- MVP의 비진료 반출은 요청자와 다른 계정의 담당자 검토를 요구한다. 개인정보 탐지가 0건이어도 자동 반출을 허용하지 않는다.
- 미지원·파싱 실패·위치 불일치·검증 미완료는 관리자나 검토자가 강제로 승인할 수 없다. 유효한 처리 사본을 새로 생성·검증해야 한다.
- 마스킹이 필요한 반출에서 처리 실패를 원본 전송으로 대체하지 않는다.
- QR는 자료·목적·수신처·기간에 연결된 일회용 티켓이다. QR 소지만으로 신원 확인과 인가를 완료하지 않는다.
- 현재 범위는 가상 병원·합성 환자 PoC다. 실제 병원 연동, 실제 환자 데이터 사용, 한국어 성능 검증, 법적 익명화 인정이 완료되었다고 쓰지 않는다.

P0 DICOM 지원 범위는 **고전적 단일 프레임 CT와 단일 프레임 Secondary Capture의 합성 샘플, Explicit VR Little Endian**이다. SOP Class·프레임·전송 구문 등 모든 조건을 함께 만족해야 한다. 미지원 객체가 섞인 작업은 전체 반출을 보류하고, 지원 객체만 보내려면 별도로 허가된 범위의 새 작업을 만든다.

태그 처리 후에도 픽셀의 개인정보와 외형을 확인해야 한다. `BurnedInAnnotation=NO`만으로 영상이 안전하다고 판정하지 않는다. P1 OCR·픽셀 마스킹을 P0에 이미 구현된 기능처럼 쓰지 않는다.

### 3. 용어와 계약을 구별하라

다음 세 계층을 별도 필드로 명세하라.

**탐지 계층**

- 모델 기본 라벨: `private_person`, `private_address`, `private_email`, `private_phone`, `private_url`, `private_date`, `account_number`, `secret`.
- 기준 계획의 시스템 유형: `PERSON`, `KR_IDENTIFIER`, `HOSPITAL_ID`, `CONTACT`, `DATE`, `SECRET`, `CLINICAL_CONTENT`.
- 기본 모델 라벨과 병원용 분류를 혼용하지 말라. 시스템 프롬프트로 모델의 고정 라벨을 확장했다고 가정하지 말라.
- 8개 모델 라벨 모두에 대해 시스템 유형 매핑과 문맥 조건을 적어라. 현재 체계에 자연스럽게 대응하지 않는 항목은 미해결 또는 유형 확장 제안으로 명시하라. `account_number`를 병원번호로 일괄 해석하거나, 모든 URL을 하나의 처리로 단정하지 말라.
- 모델 점수가 제공·검증되지 않으면 `score: null`을 사용한다. 임의의 신뢰도 수치나 임계값을 실제 모델 출력처럼 쓰지 않는다.

**필드 조치 계층**

`KEEP / REMOVE / REPLACE / SHIFT / REVIEW`

각 조치의 입력 조건, 매개변수, 출력 형태, 적용 불가 조건을 정의하라. `REVIEW`는 검토 필요 표시이며, 그 자체로 개인정보를 제거한 변환 결과가 아님을 명시하라. `KEEP`도 반출 승인과 별개다.

**작업·검토·반출 계층**

| 필드 | 기준 계획의 값 |
| --- | --- |
| job_status | PENDING, PROCESSING, SUCCEEDED, FAILED, UNSUPPORTED, CANCELLED |
| current_stage | RESOLVE, EXTRACT, DETECT, TRANSFORM, VALIDATE, FINALIZE |
| policy_decision | UNDECIDED, TRANSFORM_REQUIRED, REVIEW_REQUIRED, ALLOW, DENY |
| review_status | PENDING, APPROVED, REJECTED, STALE |
| release_status | NOT_READY, READY, SENDING, SENT, UNKNOWN, REVOKED, EXPIRED |
| artifact_state | QUARANTINED, VALIDATED, EXPIRED, PURGED |

처리 전 요청이 거부되어 job이 생성되지 않은 경우는 “작업 미생성”으로 설명하라. 이를 새로운 job enum으로 추가하지 말라. 아직 존재하지 않는 검토·사본 레코드에 임의의 완료 상태를 부여하지 말라.

`SUCCEEDED`, `APPROVED`, `ALLOW`, `READY`의 의미를 구별하고, `release_eligible`은 서버가 최신 조건을 재계산한 결과이지 재사용 가능한 권한 증명서가 아님을 명시하라.

### 4. 문서에 반드시 완성할 내용

#### 4.1 목적별 처리정책

기존 진료 공유와 네 가지 비진료 목적을 비교하는 정책 표를 작성하라. 각 목적별로 다음을 채워라.

- 허용 입력과 합성 출처·이용 근거의 확인 조건.
- 이름·환자번호·연락처·생년월일·검사일·기관명·임상정보에 대한 기본 조치.
- 필요한 임상정보와 목적에 불필요한 민감정보의 구분.
- 허용 수신처, 검토 요구, 미확인 시 기본 처리.
- 적용 프로파일, 근거 자료, 아직 제안인 결정.

목적 이름만으로 허용을 결정하지 말라. 요청자가 입력한 `purpose`나 JSON의 사용자·기관 ID를 그대로 권한으로 신뢰하지 말라. 서버가 확인한 호출자, 자료 범위, 수신처, `approved_use_ref`와 목적 등록 정보를 사용하라.

`DEMO`는 합성 출처가 확인된 자료를 사용하는 폐쇄형 시연으로 제한한다. `AI_LOCAL`은 내부 실행이라는 이유만으로 모든 원문 건강정보 사용을 허용하지 않는다. 이름을 지운 자료에 남는 진단·희귀질환·직업·지역·날짜 조합도 목적 적합성과 재식별 단서 관점에서 다뤄라.

진료 필요성, 처리 근거, 익명성, 법률 준수를 모델의 라벨·점수 하나로 판정하지 말라.

#### 4.2 개인정보 유형 사전과 조치 규칙

정책 규칙에 `HPP-P001` 형식의 고유 ID를 부여하고, 최소 20개 규칙을 구체적으로 작성하라. 서로 같은 규칙을 이름만 바꾸어 수를 채우지 말라.

각 규칙은 다음을 포함해야 한다.

- 대상 필드·구간·문맥과 적용 목적.
- 규칙이 발동하는 조건 및 발동하지 않는 예외.
- 필드 조치와 치환 토큰·날짜 처리 등 필요한 매개변수.
- 다른 규칙과의 충돌 우선순위.
- 사후 검증과 검토 완료 조건.
- 제안한 사유 코드, 근거, 연결되는 요구사항·시험 ID.

표가 지나치게 넓어지면 3열 요약표와 규칙별 설명으로 나누어라.

다음 판단을 빠짐없이 구체화하라.

1. 환자·보호자·의료진 이름, 역할이 불확실한 이름, 동명이인, 한 문서에 반복되는 동일 인물.
2. 주민등록번호·외국인 식별번호 형태, 구분자 변형, 체크섬이 틀린 민감 후보.
3. 기관별 환자번호·접수번호와 일반 숫자의 구별.
4. 주소·전화·이메일, 공용 연락처와 개인 연락처의 구별에 필요한 근거.
5. 공개 URL, 개인 식별자를 포함한 URL, 인증 토큰이 포함된 URL.
6. 생년월일·검사일·퇴원일·상대 날짜·나이·날짜가 아닌 측정값.
7. 토큰·비밀번호·비밀키 등 비밀정보.
8. 진단·약물·용량·단위·좌우·부정 표현·시간 순서와 개인정보 후보의 충돌.
9. 희귀 사례·직업·세부 지역·시간 조합의 추가 검토 조건.
10. DICOM 이름·Patient ID·UID·날짜·자유서술·중첩 정보·Private 정보·픽셀 정보의 정책 경계.

기관별 식별자 정규식이나 사전은 실제 설정을 제공받지 않았다면 예시라고 표시하라. 체크섬 불일치를 반출 허용 근거로 삼지 말라. 약물 용량·검사 수치가 숫자라는 이유만으로 환자번호처럼 변환되지 않도록 반례를 제시하라.

#### 4.3 변환의 결정성과 임상정보 보존

텍스트 위치 기준은 원문 Unicode 코드포인트의 `[start, end)`다. Python 문자 인덱스, JavaScript UTF-16 인덱스, UTF-8 바이트 위치를 혼용하지 않도록 예시로 설명하라.

원문을 보존하고 정규화 사본에서 원문 위치로 되돌리는 계약을 작성하라. NFC/NFD, CRLF, 이모지, 제로폭 문자, 접두 문맥 추가 시 위치 복원 조건을 포함하라. 위치 검증 실패는 `OFFSET_MISMATCH`이며 사람이 승인해서 그대로 전송할 수 없다.

모델·규칙의 겹치는 구간은 원문 덮임과 근거를 보존하여 통합한다. 서로 다른 유형·조치가 충돌할 때 적용 순서와 검토 조건을 정하라. 임상정보 보존 규칙이 확인된 식별정보를 그대로 내보내는 우회가 되지 않도록 하라. 검토로 조치를 변경하면 사본 재생성·재검증과 승인 대상 버전 변경을 명시하라.

치환은 확정 구간에 결정적으로 적용한다. 임상 문서를 LLM으로 통째로 재작성하거나 임상 의미를 추측하여 보완하는 처리는 포함하지 말라.

가명은 승인된 기관·프로젝트·수신 범위에 연결한다. 같은 범위의 동일 자료를 재시도할 때 일관성을 유지하되, 다른 목적이나 수신처에 전역적으로 연결되는 가명을 만들지 말라. 이름 문자열이 같다는 이유만으로 두 사람을 동일 환자로 연결하지 말라.

날짜 `SHIFT`는 환자·프로젝트 범위에서 관계를 보존할 수 있는 조건, 필수 날짜를 제거할 수 없는 경우, 부분 날짜·오류 날짜·범위 초과 처리, 재처리 일관성을 정의하라. 이동 폭을 선택한다면 명세서의 제안으로 표시하고, 특정 범위의 이동이 익명성을 보장한다고 쓰지 말라. 연령 구간화도 정확한 구간·의미 손실·검토 조건을 제안해야 하며 새 조치 enum을 몰래 만들지 말라.

#### 4.4 DICOM에 적용할 정책 경계

DICOM의 전체 저수준 구현 명세를 새로 쓰지 말고, 텍스트 정책과 DICOM 정책의 연결·차이를 명세하라.

- 원본 보존과 처리 사본의 독립성.
- 구조화 필드, 자유서술, 중첩 속성, 원본 속성·Private 정보의 처리 범위.
- Patient ID와 Study/Series/SOP Instance UID의 목적별 매핑 및 참조 일관성.
- SOP Class UID와 Transfer Syntax UID를 개인 식별용 UID처럼 일괄 변환하지 않는 규칙.
- 생년월일·검사 날짜·시간 관계와 필수 형식의 충돌 처리.
- 태그 정제와 픽셀·외형 검토의 구별.
- 미지원 형식과 혼합 작업의 보류 조건.

태그 번호, VR, IOD 요구사항, DICOM 프로파일의 규범적 조치를 기재한다면 공식 표준에서 확인한 근거를 붙여라. 대표 태그 몇 개의 처리를 전체 DICOM 비식별 표준 준수로 확대 해석하지 말라. 빈 값과 속성 삭제가 형식상 동일하다고 가정하지 말라.

#### 4.5 판정 우선순위와 반출 결정표

다음 흐름을 평가 순서가 명확한 규칙으로 작성하라.

1. 호출자·기관·원본 범위·목적·수신처·등록 근거 확인.
2. 지원 형식과 입력 무결성 확인.
3. 모델·규칙 처리 및 구간 검증.
4. 변환·사후 검증·필수 검토 항목 해소.
5. 고정된 사본 버전·manifest digest·정책 버전에 대한 검토.
6. 반출 직전 최신 권한·동의·수신처·만료·철회 상태 재확인.

최소 12개 조합의 결정표를 작성하라. 표에는 전제 조건, 관련 상태, 허용 행동과 금지 행동을 포함하라. 필요한 경우 처리 상태 표와 반출 표를 분리하라.

반드시 포함할 조합:

- 적법한 기존 진료 요청과 무권한 진료 요청, AI 중단 시 각각의 처리.
- 비진료의 정상 변환·검증 완료 후 검토 대기.
- 개인정보 탐지 0건이지만 아직 검토 전인 작업.
- 모델 미탐지와 필수 규칙 탐지가 공존하는 작업.
- 모델 장애·timeout, 오프셋 오류, 파싱 실패, 미지원 객체 혼합.
- 임상 표현과 삭제 후보가 충돌하여 조치가 미확정인 작업.
- 유효한 동일 사본 승인과 최신 권한 확인까지 완료된 정상 반출.
- 승인 후 사본·정책·목적·수신처가 달라진 작업.
- 권한 철회, 만료, QR 재사용, 잘못된 수신기관.
- 전달 ACK를 잃어 `UNKNOWN`인 작업의 재확인 조건.

검토가 무엇을 해결할 수 있고 무엇을 우회할 수 없는지 적어라. 미확정 조치의 해결과 기술적 검증 실패의 강제 승인을 혼동하지 말라. 승인 후 사본이 달라지면 이전 승인을 재사용하지 않는다. 로그와 오류 응답에는 원문·치환 매핑·QR 원문·키를 포함하지 않는다.

#### 4.6 구현으로 옮길 정책 설정 예시

이 문서에서 제안하는 설정 형식임을 명시하고, 파싱 가능한 YAML 예시를 작성하라.

- 상위 `research-v1`과 하위 `text-research-v1`, `dicom-research-v1`의 참조 관계.
- 텍스트 미리보기 `text-demo-v1`의 별도 범위.
- 정책 ID·버전, 목적·형식, 규칙 참조, 조치 매개변수.
- 지원 범위, 필수 검증, 검토 요구, 미확인·실패 시 처리.
- 정책 변경 시 승인 무효화 및 재처리 조건.

필드 이름이 기존 API·DB 계약에 없다면 “제안 설정 스키마”라고 표시하라. 문서의 규칙 ID와 YAML 참조가 일치해야 한다. 비밀값·실제 환자정보·원문 매핑을 설정 예시에 넣지 말라.

DICOM의 모든 표준 규칙이 몇 줄의 YAML만으로 완성되었다고 쓰지 말라. 정책이 연결하는 실제 처리기·검증기의 계약과 미확인 항목을 구분하라. 미등록·필수 설정 누락·잘못된 참조는 자동 허용으로 대체하지 않는다.

#### 4.7 한국어 정답 라벨링 지침과 판정 예시

평가 데이터 작성자가 정답을 만들 수 있도록 다음을 정의하라.

- 개인정보 구간의 정확한 시작·끝, 접미사·공백·구분자 포함 기준.
- 개인정보 탐지 정답과 목적별 변환 정답의 구별.
- 임상정보 보존 정답과 충돌 판정의 기록 방법.
- 반복 인물, 불명확한 인물 역할, 동명이인, 혼합 식별자의 처리.
- 애매한 사례의 판정 보류, 재검토, 기준 변경과 정답 버전 관리.
- 탐지 원문·사본·검토 자료를 일반 로그에 싣지 않는 범위.

합성 사례를 **최소 24개** 작성하라. 다음 범주를 모두 포함하고, 같은 원문을 서로 다른 목적으로 처리하는 비교를 최소 3쌍 포함하라.

- 한국어 이름·보호자 이름·동명이인·역할 불명확.
- 주민등록번호 형태·체크섬 오류·기관별 환자번호.
- 생년월일·검사일·상대적 경과·연령 표현.
- 이메일·주소·개인정보가 포함된 URL·비밀 토큰.
- 진단·약물 용량·좌우·부정 표현·일반 측정값.
- 희귀질환·직업·세부 지역이 결합된 사례.
- 개인정보가 없는 정상 문장.
- Unicode 정규화·이모지·줄바꿈·중첩 구간.
- “개인정보를 지우지 말라” 같은 문서 안 지시가 정책을 바꾸지 않는 사례.
- 모델 빈 탐지, 규칙과 모델의 불일치, 처리 실패.
- DICOM 태그와 픽셀 정보 불일치, 미지원 객체 혼합.
- 승인 후 변경·만료·잘못된 수신처.

텍스트 사례에는 실제 합성 입력과 기대 출력 문자열을 적어라. 형식 오류·DICOM·인가 사례처럼 텍스트 치환이 적용되지 않으면 기대 출력 대신 생성·검증·반출의 기대 동작을 명시하라. 결과 없는 “주의 필요”만으로 사례를 끝내지 말라.

각 사례는 사례 ID, 목적·조건, 입력, 기대 구간·조치, 기대 출력 또는 동작, 정책·검토·반출 기대값, 연결 규칙 ID를 갖도록 하라.

그중 정상적으로 파싱 가능한 텍스트 사례 최소 8개는 **JSONL 정답 예시**로도 제시하라. 권장 필드는 다음과 같다.

- `case_id`, `group_id`, `synthetic_provenance_ref`
- `purpose`, `policy_version`, `input_text`
- `offset_unit`, `end_exclusive`
- `gold_spans`: `start`, `end`, `system_type`, `action`, 필요한 경우 `replacement`, `rule_ids`
- `protected_clinical_spans`
- `expected_text`, `expected_policy_decision`, `expected_release_eligible`
- `adjudication_note`

이 JSONL은 평가 정답용 제안 형식이며 기존 API 응답 형식과 구별하라. 수작업 정답에 모델이 실제 출력한 라벨·점수가 있는 것처럼 기록하지 말라. 탐지 성능 평가용 정답과 구간 병합·치환 정답을 분리하여, 후처리가 탐지 오류를 숨기지 않도록 하라.

각 `input_text[start:end]`와 정답 대상이 일치하는지 확인하라. 도구로 검증할 수 있다면 JSON 파싱과 코드포인트 위치, 기대 문자열을 확인하고, 검증하지 못했으면 검증 완료라고 쓰지 말라.

모든 사례는 합성 데이터로 만들고 실제 환자정보·자격증명·동작하는 티켓을 사용하지 말라. 합성 출처는 메타데이터에 기록하되 모든 본문에 “가상환자” 같은 탐지 힌트를 반복 삽입해 평가를 쉽게 만들지 말라.

이 문서에서는 판정 지침과 대표 정답을 작성한다. 기존 계획의 600건 전체 데이터셋이 생성되었다고 주장하지 말라.

#### 4.8 요구사항·시험 추적과 변경 관리

정책 규칙 → 판정 사례 → 기존 요구사항 `PF-R01~PF-R15` → 기존 시험 `PF-T01~PF-T20`의 추적표를 작성하라. 실제 관련 있는 항목만 연결하고, 기존 ID의 뜻을 재정의하지 말라.

특히 다음 연결을 확인하라.

- 필수 규칙과 모델 미탐지: PF-R02, PF-T04.
- 임상정보 보존·Unicode: PF-R06, PF-T06·PF-T07.
- DICOM 처리·참조·픽셀 경계: PF-R07 및 P1의 PF-R15, PF-T09~PF-T12.
- 실패 시 반출 거부: PF-R05, PF-T08·PF-T09.
- 고정 사본 승인·권한·QR: PF-R08·PF-R09, PF-T14~PF-T17.
- 로그에 금지 값이 남지 않음: PF-R10, PF-T19.
- 정상 승인·전송: PF-T20.

필요한 새 사례는 별도 ID로 추가하고 기존 시험을 덮어쓰지 말라. 현재 실행 결과는 실제 실행 증거가 없다면 `NOT_RUN`이다.

기존 계획의 평가 규모 600건과 개발·검증·시험 분리 240/120/240, 규칙 단독·모델 단독·결합 방식 비교, 사람 수정 전 사본 평가 원칙을 유지하라. Recall·Precision·임상정보 보존 등의 잠정 합격 목표를 이번 문서가 실제 달성 수치로 바꾸지 않는다.

정책 변경 시 다음의 영향을 명세하라.

- 새 버전 발급과 이전 버전의 유효 범위.
- 실행 중 작업의 계속·중단·재처리 기준.
- 기존 승인 사본, QR·키 릴리스, 만료·철회에 대한 처리.
- 정답 라벨과 회귀 사례의 수정 이력.
- 독립 시험 집합의 누출 방지. 시험 결과를 보고 기준을 통과하도록 정책·정답을 바꾸는 경우 새 평가가 필요함.
- 이미 수신된 평문을 철회만으로 회수할 수 있다고 가정하지 않는 한계.

#### 4.9 확인 항목과 완료 기준

문서 끝에 확인 항목을 중요도순으로 최대 10개 제시하라. 각 항목에는 현재 제안값, 결정에 필요한 증거, 담당 역할, 미확정 시 처리, 영향받는 규칙·시험을 적어라. 사람 이름·병원 승인·법률 검토 결과를 만들어내지 말라.

다음 조건을 만족하는지 문서 자체를 점검하라.

1. 목적별로 무엇을 남기고 무엇을 처리하는지 판단 가능한가?
2. “필요 시”, “적절히”, “애매하면 검토”에 조건·기본 조치·해소 기준이 붙어 있는가?
3. 모델 라벨, 시스템 유형, 필드 조치, 최종 반출 결정이 분리되어 있는가?
4. 정상 입력의 처리·검토·허용 경로와 실패·거부 경로가 모두 있는가?
5. 동일한 원문·범위·정책 버전의 재처리 결과를 일관되게 만들 수 있는가?
6. YAML, 규칙 표, 사례, JSONL의 ID·조치·기대값이 일치하는가?
7. 개인정보 보호와 임상 의미 보존이 충돌할 때 해결 절차가 있는가?
8. 검토나 관리자 권한으로 기술적 실패를 우회할 수 없게 되어 있는가?
9. 실제 구현·측정·승인 여부를 과장하지 않았는가?
10. 정책 엔진 구현과 정답 라벨링을 시작할 수 있을 만큼 구체적인가?
