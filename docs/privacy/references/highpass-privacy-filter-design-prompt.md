# 하이패스 OpenAI Privacy Filter 의료개인정보 마스킹·필터링 설계 프롬프트

작성 기준일: 2026-09-06  
사용 방법: 이 문서 전체를 설계용 AI에 입력한다. 저장소나 최신 요구사항 문서가 있다면 함께 제공한다. 문서 안의 설계 후보와 목표값은 구현 완료 사실이나 측정 결과가 아니다.

---

## 1. 역할과 작업 목표

당신은 의료영상 시스템 아키텍트, DICOM·DICOMweb 전문가, 개인정보 보호 엔지니어, 로컬 AI 추론 엔지니어, 의료정보 보안 검토자, 캡스톤 프로젝트 설계자의 관점으로 검토한다.

기존 **하이패스(Highpass) 의료영상 공유·전송 프로젝트**에 **OpenAI Privacy Filter**를 도입하여 의료개인정보를 탐지하고, 이용 목적에 맞게 마스킹·가명처리·반출 제한을 수행하는 구조를 설계하라.

목표는 다음과 같다.

> 원본 의료영상과 진료에 필요한 정보의 정확성을 유지하면서, 불필요한 개인정보가 화면·문서·로그·연구 또는 AI 반출 경로로 노출되는 것을 줄인다. 개인정보 탐지에는 로컬 Privacy Filter와 규칙을 활용하고, 처리·반출 여부는 하이패스의 권한·목적별 정책으로 결정한다.

이번 산출물은 **타당성 검토와 구체적인 설계·구현계획서**다. 저장소가 제공되면 현재 구조를 읽고 연결 지점을 제시하되, 이번 설계 작업에서 설치·코드 변경·배포를 실행하지 않는다. 제공되지 않은 환경, API, 구현 상태를 만들어내지 않는다.

---

## 2. 유지할 프로젝트 전제

다음 내용을 설계의 출발점으로 사용한다. 단, 구성요소가 실제로 구현·검증되었는지는 제공 문서와 저장소에서 따로 확인하라.

| 구분 | 설계 전제 |
| --- | --- |
| 핵심 목적 | 환자 동의와 적절한 권한을 바탕으로 병원 간 의료영상을 조회·공유한다. |
| 원본 보관 | 원본 DICOM은 A병원의 PACS/Orthanc에 유지한다. |
| 데이터 흐름 | B병원이 DICOMweb으로 원격 조회하고, 필요한 경우에만 B병원 PACS에 선택적으로 전송한다. |
| 제어 영역 | Highpass Control Plane은 인증·동의·정책·단기 권한·감사·최소 메타데이터를 담당한다. |
| 영상 전달 영역 | 병원 Edge Gateway/Connector가 DICOMweb 요청과 영상 전달을 담당한다. Edge 간 연결과 Cloud Relay 사용 여부는 기존 설계에 맞춘다. |
| QR | 동의와 제한된 전송권한을 연결하는 일회용 티켓 용도다. QR의 존재만으로 사용자 인증이나 반출 승인이 성립하지 않는다. |
| 모바일 | 암호화 저장·재전송 요구를 고려하여 검증 위치와 전달 대상을 설계한다. 구현 완료로 간주하지 말고 현재 범위와 후속 범위를 표시한다. |
| 검증 환경 | 가상 A·B병원, 합성 환자정보, 사용권과 개인정보 상태를 확인한 샘플 DICOM을 활용하는 PoC다. |
| 현재 확인이 필요한 사항 | Gateway/OHIF/Orthanc 연결, 토큰·동의 구현, Docker 실행 상태, 실제 CPU·RAM·GPU, 외부 Staging 연동 상태 |
| 프로젝트 경계 | SOC 관제나 N2SF 등급분류 시스템으로 범위를 확대하지 않는다. 이번 AI의 핵심 기능은 개인정보 탐지다. |

과거에 AI가 MVP 제외 항목이었다면 이번 요청을 **AI 개인정보 보호 기능 추가 제안**으로 다루고, 이에 따른 요구사항 변경과 추가 비용을 표시하라. 실제 병원 운영 승인이나 진단 정확도 검증이 완료되었다고 서술하지 않는다.

## 3. 모델에 관하여 먼저 확인할 사실

아래는 작성 기준일에 공식 자료로 확인한 출발점이다. 실행 시점의 문서와 체크포인트를 다시 확인하고 변경 여부를 표시하라.

| 항목 | 확인된 내용 |
| --- | --- |
| 모델 식별자 | `openai/privacy-filter` |
| 기본 역할 | 텍스트의 개인정보 구간을 찾는 양방향 토큰 분류 모델 |
| 결과 해석 | 개인정보 후보 구간과 유형을 탐지하며, 시스템이 이를 받아 후속 마스킹·삭제·대체 등을 수행한다. |
| 공개 규모 | 총 1.5B 파라미터, 활성 50M 파라미터 |
| 입력 길이 | 공식 소개상 최대 128,000 토큰. 실제 장비에서 처리 가능한 길이·지연·메모리는 별도 측정한다. |
| 배포 | 오픈 웨이트, Apache 2.0 라이선스, 로컬 실행 가능 |

근거: [OpenAI 공식 소개](https://openai.com/ko-KR/index/introducing-openai-privacy-filter/), [OpenAI 공식 모델 배포 페이지](https://huggingface.co/openai/privacy-filter).

공식 기본 탐지 범주는 다음과 같다.

`private_person`, `private_address`, `private_email`, `private_phone`, `private_url`, `private_date`, `account_number`, `secret`

의료기록번호·주민등록번호·진단명 등이 각각 독립된 기본 라벨로 제공되는 것으로 가정하지 않는다. `account_number`가 모든 병원 식별번호를 안정적으로 탐지한다고 가정하지 않는다.

다음 구분을 명확히 하라.

- **탐지 기준과 처리 정책:** 모델이 무엇을 탐지하는지와 하이패스가 그 결과를 어떻게 처리하는지는 구분한다.
- **추론 조정과 학습:** 디코딩 설정 조정은 정밀도·재현율의 균형을 바꾸는 수단이다. 자연어 시스템 프롬프트만으로 모델의 기본 라벨 체계가 확장되는 것으로 설계하지 않는다.
- **텍스트와 영상:** DICOM 바이너리, 영상 픽셀, 얼굴, QR 이미지를 모델이 직접 해석하는 것으로 가정하지 않는다.
- **개인식별정보와 의료정보:** 이름을 제거해도 질병·검사 결과·희귀 사례·날짜 조합 등에 남는 노출 위험을 별도로 평가한다.
- **탐지 결과와 안전성:** 탐지 결과가 비어 있다는 이유만으로 익명정보이거나 자유롭게 반출 가능한 정보라고 판단하지 않는다.
- **언어 성능:** 영어 중심 모델의 공개 성능을 한국어 의료문서의 성능으로 옮겨 쓰지 않는다.

근거: [OpenAI Privacy Filter 모델 카드](https://cdn.openai.com/pdf/c66281ed-b638-456a-8ce1-97e9f5264a90/OpenAI-Privacy-Filter-Model-Card.pdf).

공식 저장소는 CPU와 GPU 실행을 안내한다. **공식 Python 런타임을 병원 내부 추론 서비스로 감싸는 방안**을 우선 검토하되, 라이브러리 버전과 실제 입출력 계약을 확인하라. 일반 채팅형 LLM처럼 Ollama에 바로 올리거나 OpenAI의 호스팅 API를 호출할 수 있다고 임의로 가정하지 않는다. CPU 실행 지원과 목표 응답시간 충족은 별개다.

근거: [OpenAI 공식 저장소](https://github.com/openai/privacy-filter).

## 4. 우선 결정해야 할 설계 쟁점

각 쟁점에 대해 **권고안 → 이유 → 적용 조건 → 검증 방법**을 제시하라.

1. AI의 1차 적용 대상을 판독문·의뢰서·비정형 메타데이터 중 어디로 정할 것인가?
2. 환자 식별이 필요한 진료 공유와 연구·교육·데모·AI 반출에 각각 어떤 정책을 적용할 것인가?
3. 원문 개인정보를 처리할 신뢰 경계를 어디에 둘 것인가?
4. 규칙 기반 탐지와 Privacy Filter가 일치하지 않을 때 어떻게 결정할 것인가?
5. AI 장애, OCR 실패, 미지원 파일, 불완전한 탐지에 어떻게 대응할 것인가?
6. DICOM 원본, 처리 사본, 환자 매핑을 어떻게 구별하고 보호할 것인가?
7. 한국어 의료문서에서 AI가 규칙 단독보다 실제로 기여했음을 어떻게 증명할 것인가?
8. 현재 캡스톤 일정과 장비에서 완성할 최소 범위는 무엇인가?

권고 출발점은 다음과 같다.

> **송신 병원 Edge 내부의 개인정보 처리 서비스 + 구조화된 식별자 규칙 + Privacy Filter 텍스트 탐지 + 목적별 정책 엔진 + 처리 사본 검증 + 승인된 반출**.

이를 무조건 정답으로 받아들이지 말고, 현재 하이패스 구조와 성능·운영 비용에 비추어 평가하라.

## 5. 전체 아키텍처와 신뢰 경계

### 5.1 진료 공유 경로

인증된 진료 목적의 공유는 기존 동의·권한·환자 매칭·Study/Series 범위 검증을 거친다.

- 진료용 환자 식별정보를 무조건 가려 잘못된 환자 매칭을 유발하지 않는다.
- 역할과 화면의 목적에 따라 표시할 최소 필드를 정한다.
- Privacy Filter를 모든 WADO 영상 프레임의 필수 동기 처리 단계로 넣지 않는다.
- AI 장애가 발생했을 때 기존 진료 경로가 어떤 통제를 유지하며 동작할지 명시한다.
- 반출 제한을 우회하려고 요청자가 목적을 `clinical`로 바꾸는 공격은 서버의 권한·수신기관·행위 검증으로 차단한다.

### 5.2 연구·데모·AI 등 목적별 반출 경로

다음 단계의 위치·책임·입출력·실패 처리를 구체화하라.

1. 서버가 요청자, 이용 목적, 법적 근거 또는 필요한 동의, 대상 자료와 수신자를 확인한다.
2. 송신 병원의 신뢰 영역에서 자료 유형을 판별하고 내용을 추출한다.
3. 구조화된 필드에는 규칙을, 비정형 텍스트에는 규칙과 Privacy Filter를 적용한다.
4. 정책 엔진이 보존·삭제·가명 대체·검토 보류·반출 차단을 결정한다.
5. 원본을 유지한 채 목적별 처리 사본을 만든다.
6. 사본 전체와 부속 파일에서 잔존 식별정보·형식 오류·임상정보 손상을 검사한다.
7. 필요한 사람의 검토와 반출 직전 재인가를 거친다.
8. 검증된 사본만 지정 수신처로 전달하고 최소 감사정보를 남긴다.

**마스킹이 필요한 반출 경로에서는 추론 실패나 검증 미완료 시 원본을 대신 보내지 않는다.** 이 실패 정책과 진료 경로의 가용성 정책을 혼동하지 않는다.

### 5.3 배치 비교

다음 세 가지를 3열 표로 비교하라.

| 배치 후보 | 장점·제약 | 하이패스 적용 판단 |
| --- | --- | --- |
| 송신 병원 Edge 내부 | 원문 처리 위치, 병원별 운영·자원 부담 | 우선 검토 |
| 중앙 서버 | 처리 효율, 원문 전송·집중에 따른 신뢰 경계 변화 | 필요 조건 제시 |
| 브라우저·모바일 | 사용자 미리보기, 기기 자원, 우회 가능성 | 최종 반출 통제와의 역할 구분 |

서버의 최종 반출 통제를 클라이언트의 마스킹 결과만으로 대체하지 않는다. 제어 메시지와 실제 의료데이터의 화살표를 구별한 **한글 Mermaid 구성도**를 작성하라. 도식은 관계별로 나누고 가로 노드는 다섯 개를 넘기지 않는다.

## 6. 데이터별 담당 기능과 처리 정책

아래 내용을 확장하여 데이터별 처리표를 작성하라.

| 데이터 | 주 담당 처리 | 반드시 확인할 사항 |
| --- | --- | --- |
| DICOM 구조화 태그 | DICOM 비식별 규칙·목적별 프로파일 | 필수 속성, UID 참조, 중첩 Sequence, Private Tag |
| 판독문·의뢰서·비정형 메모 | Privacy Filter + 한국어·병원 식별자 규칙 | 이름·연락처·식별번호 누락, 임상정보 과다 삭제 |
| DICOM 자유 텍스트 속성 | DICOM 파서 + 텍스트 탐지 | 올바른 속성에 결과를 되돌리고 형식 유지 |
| 영상에 새겨진 글자 | 로컬 OCR + 좌표 연결 + 탐지 + 픽셀 처리 | OCR 누락, 여러 프레임, 처리 결과 검증 |
| 얼굴·신체 외형 등 시각적 식별요소 | 별도 영상 처리 또는 검토 경로 | 텍스트 탐지와 다른 기능임을 명시 |
| QR·전송 티켓·모바일 패키지 | 스키마 제한·권한·암호화·수명주기 정책 | QR·파일명·매니페스트·미리보기의 개인정보 |
| 로그·오류·APM 추적 | 처음부터 허용 필드만 기록, 규칙 기반 제거 | 원문·토큰·모델 입력·디버그 출력 노출 |

서로 다른 조치를 모두 “마스킹”으로 부르지 말고 **화면 가림, 삭제, 가명 대체, 암호화, 반출 차단**을 구별하라.

정책 예시에는 다음을 포함한다.

- **진료 공유:** 필요한 환자 매칭 정보와 임상정보의 정확성을 유지한다.
- **연구·교육:** 직접 식별자 제거와 가명화 범위를 정하고, 날짜·나이·희귀질환 등 조합에 따른 위험을 평가한다.
- **데모·발표:** 합성 데이터를 우선하고, 미검증 의료데이터가 공개 시연으로 유입되지 않게 한다.
- **AI 입력·반출:** 이름 등 직접 식별자뿐 아니라 입력 목적에 불필요한 의료정보도 최소화하고 수신 환경을 확인한다.

외부 AI 전송은 기본 필수 기능으로 넣지 않는다. 필요한 확장안에서만 목적·수신자·처리 근거·잔여 위험을 검토한다.

## 7. DICOM과 픽셀 처리 설계

DICOM 처리의 기준으로 **PS3.15 Annex E의 Basic Application Level Confidentiality Profile과 선택 옵션**을 검토한다. 작성 당시 확인한 현행 문서는 2026c이며 실행 시점의 판본을 기록하라.

### 7.1 태그와 처리 사본

다음을 설계하라.

- PatientName, PatientID, PatientBirthDate, AccessionNumber, 기관·담당자 정보, 자유 텍스트 속성의 목적별 처리표.
- 실제 태그 번호, VR, IOD 요구사항, 프로파일 조치의 원문 확인.
- 최상위 속성과 중첩 Sequence의 재귀적 처리.
- Private Tag, 파일 메타정보, 파일명, 썸네일, 부속 문서의 노출 점검.
- 필요한 식별 UID의 일관된 매핑과 참조 관계 유지. SOP Class UID 등 모든 UID를 일괄 무작위 변경하지 않는다.
- 한국어 인코딩, 필수 값, 길이·형식·참조 무결성 확인.
- 날짜 변환 시 목적상 필요한 상대적 시간 간격과 동일 사례 내 일관성 유지.
- 가명 매핑의 별도 보호와 승인 범위 내 사용. 단순 무키 해시를 안전한 가명화로 간주하지 않는다.
- 실제 수행한 처리에 맞는 비식별 방법 기록. 검증 전에 완료 표시를 넣지 않는다.
- 원본과 처리 사본의 저장·조회 경로를 구별하고 원본을 덮어쓰지 않는다.

근거: [DICOM PS3.15 Annex E](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/chapter_e.html), [Basic Application Level Confidentiality Profile](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_e.2.html).

### 7.2 영상에 새겨진 개인정보

**영상 픽셀 내 글자는 텍스트 모델만으로 제거되지 않는다.** 다음을 별도 설계하라.

- OCR 텍스트의 문자 구간을 원본 영상 좌표·SOP Instance·프레임에 연결한다.
- 영상 위에 검은 사각형을 표시하는 것과 실제 저장 픽셀을 변경하는 것을 구별한다.
- 알려진 환자 식별자와의 대조, OCR 품질, 탐지 결과를 함께 검토한다.
- 모든 대상 프레임의 처리 완료 여부를 확인한다. 일부 프레임의 성공을 전체 영상의 성공으로 처리하지 않는다.
- `BurnedInAnnotation=NO`만으로 식별정보 부재를 확정하지 않는다.
- 병변·좌우 표시·측정값 등의 훼손 위험이 있거나 픽셀 검증이 불완전하면 검토로 넘긴다.
- 얼굴 재구성 등 시각적 재식별 위험은 OCR과 별도 항목으로 평가한다.

근거: [Clean Pixel Data Option](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_e.3.html), [Clean Recognizable Visual Features Option](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_e.3.2.html).

MVP에서는 지원할 SOP Class·모달리티·전송 구문·프레임 범위를 제한하라. 미지원 DICOM SR, 캡슐화 PDF, 압축·다중 프레임 영상 등이 반출 요청에 포함되면 **그대로 통과시키지 않고 미지원 상태로 보류**한다. 후속 지원 범위를 따로 제안한다.

## 8. Privacy Filter 추론·후처리 구현 명세

### 8.1 추론 서비스

- 병원 Edge 내부에 독립 프로세스 또는 컨테이너로 배치하는 방안을 제시한다.
- 모델을 매 요청마다 다시 로딩하지 않는 구조와 동시성·큐·시간제한을 설계한다.
- 작은 텍스트 요청의 동기 처리와 문서·영상 처리 작업의 비동기 처리를 구분한다.
- 전체 1.5B 가중치와 런타임 메모리를 고려한다. 활성 50M이라는 수치만으로 RAM 사용량을 산정하지 않는다.
- CPU/GPU별 최초 로딩, 준비된 상태의 응답시간, 입력 길이별 메모리·처리량을 측정하는 방법을 제시한다.
- 공식 Python 런타임을 기본 후보로 하고 다른 런타임·양자화는 지원 여부와 경계 탐지 품질을 확인한 뒤 선택한다.
- 설치 시 다운로드와 서비스 실행 중 네트워크 접근을 구별한다. 체크포인트를 준비한 후 추론 시 외부 송신이 없는지 검증한다.
- 원문을 명령행 인자로 넘겨 프로세스 목록에 노출시키지 않는 호출 방식을 선택한다.
- 의료 문서를 처리하는 단계에서 외부 번역 API로 한국어를 영어로 바꾸는 경로를 추가하지 않는다.

### 8.2 탐지 결과 통합

1. 규칙은 주민등록번호 형태, 연락처, 병원별 환자번호·접수번호·비밀 토큰 등 명시적 패턴을 담당한다.
2. Privacy Filter는 비정형 문맥의 개인정보 후보를 보완한다.
3. 탐지 구간의 겹침, 유형 불일치, 부분 탐지를 정해진 규칙으로 통합한다.
4. 확정적인 차단 규칙을 AI의 미탐지 결과로 해제하지 않는다.
5. 문맥이 짧은 필드는 필요한 최소 필드명·인접 문맥을 붙이는 방법과 오프셋 복원 방식을 설계한다.
6. 전체 텍스트를 생성형 모델이 다시 쓰게 하지 않고, 확인된 원문 구간을 결정적인 방식으로 치환한다.
7. 진단명·약물명·용량·단위·좌우·부정 표현·날짜 간격의 불필요한 변경을 검사한다.
8. API 키·민감 토큰이나 개인정보가 새로 포함된 오류 메시지도 점검한다.

모델에 없는 병원용 탐지 유형은 우선 외부 규칙·정책 분류로 구현하고 **기본 모델 라벨과 시스템 확장 유형**을 구별하라. 기본 성능 평가, 디코딩 조정, 오류 분석을 먼저 수행하고 파인튜닝의 필요성을 판단한다.

### 8.3 출력 스키마와 문자열 경계

공식 CLI의 JSON 예시는 원문 `text`와 탐지된 원문 조각을 포함하며, 토크나이저의 원문 복원 불일치도 표시할 수 있다. 이를 그대로 로그나 외부 응답에 복사하지 않는다.

근거: [공식 OUTPUT_SCHEMAS.md](https://github.com/openai/privacy-filter/blob/main/OUTPUT_SCHEMAS.md).

다음을 명세하라.

- 문자 위치의 단위: UTF-8 바이트, Unicode 코드포인트, UTF-16 중 실제 런타임이 사용하는 기준과 API 변환 기준.
- 시작·끝 위치의 포함/제외 규칙.
- 한글 NFC/NFD, 자모 분리, 이모지, 줄바꿈, OCR 정규화 후 원문 위치 연결.
- 범위를 벗어난 구간, 중첩 구간, 복원 불일치, 긴 입력의 청크 경계 처리.
- 실제 런타임에서 제공하는 경우에만 모델 점수를 사용하고, 점수가 없으면 이를 명시한다.
- 모델 점수·보정된 신뢰도·정책상 위험 수준을 구별한다. 존재하지 않는 confidence 필드를 만들거나 높은 점수를 안전 보장으로 쓰지 않는다.
- 분류 헤드와 공식 스팬 디코딩을 보존하고, 다른 추론 경로가 동일한 결과를 내는지 검증한다.

## 9. API·상태·권한·감사 설계

다음 API는 **하이패스가 새로 구현할 내부 API 후보**다. OpenAI가 제공하는 호스팅 API로 표현하지 않는다. 기존 경로와 이름이 충돌하면 조정하라.

| 내부 API 후보 | 목적 | 설계할 내용 |
| --- | --- | --- |
| `POST /internal/privacy/text-inspections` | 텍스트 탐지·정책 평가 | 호출자 권한, 입력 제한, 마스킹 결과, 오류 |
| `POST /internal/privacy/export-jobs` | 자료 처리 사본 생성 | 목적·수신처·자료 참조·멱등성·비동기 작업 |
| `GET /internal/privacy/export-jobs/{jobId}` | 상태·검토 결과 조회 | 기관·사용자 격리, 최소 결과 노출 |
| `POST /internal/privacy/export-jobs/{jobId}/release` | 검증된 사본 반출 | 재인가, 승인·버전·해시 일치, 재사용 방지 |

OpenAPI 형태로 옮길 수 있도록 요청·응답·오류 예시를 작성하라. 예시에 개인정보를 넣어야 한다면 명시적인 합성 데이터만 사용한다.

필수 계약:

- 요청의 purpose, scope, recipient, artifact 참조는 서버가 인증 주체와 정책에 대조한다.
- 자료 참조는 허용된 저장소에서만 해석한다. 임의 URL 가져오기, 경로 탐색, 타 기관 객체 접근을 막는다.
- 탐지 상태, 처리 작업 상태, 정책 결정을 각각 구분한다.
- 처리 상태 예시는 `PENDING / PROCESSING / SUCCEEDED / FAILED / UNSUPPORTED`, 정책 결정 예시는 `ALLOW / TRANSFORM_REQUIRED / REVIEW_REQUIRED / DENY`로 제시할 수 있다.
- `SUCCEEDED`는 검사가 끝났다는 뜻이며 자동 반출 허가를 의미하지 않는다.
- 부분 성공, AI timeout, OCR 오류, 변조된 파일, 미지원 객체, 원문 경계 불일치의 동작을 정의한다.
- 원본 참조, 처리 사본 참조, 모델·규칙·정책 버전, 처리 방법, 검토 결과, 사본 해시를 연결한다.
- 검증 뒤 파일·수신처·권한이 바뀌는 경우 기존 승인을 재사용하지 못하게 한다.
- 감사 이벤트는 원문 대신 작업 ID, 권한 있는 주체 참조, 결정, 사유 코드, 버전, 시간 등 필요한 최소 필드로 구성한다.
- 추론 입력·출력의 원문은 로그·분산 추적·오류 수집·큐·캐시에 불필요하게 남기지 않는다.
- 내부 검토 화면에서 원문 확인이 필요하면 권한과 접근 기록을 별도 적용한다.

## 10. QR·모바일·암호화 경로와의 연결

마스킹과 암호화는 별개 보호수단으로 설계하라.

- QR에는 가능한 한 불투명한 일회용 티켓만 넣고, 실제 권한·목적·수신처·대상 자료·처리 상태는 서버에서 관리한다.
- 원본 진료 패키지와 연구·데모용 처리 사본을 명확히 구별한다.
- 처리 사본은 생성·검증 이후 암호화·패키징하고, 해당 사본·수신자·목적에 권한을 연결한다.
- 미검증 반출 사본은 다운로드나 키 릴리스 대상으로 선택되지 않게 한다.
- 환자 이름이 드러나는 파일명, 매니페스트, 미리보기, 알림, QR URL의 노출을 점검한다.
- 원본과 처리 사본의 UID가 다른 경우 원래 권한의 범위가 처리 사본에 어떻게 대응되는지 설계한다.
- 재전송은 새 목적·수신처·승인 조건을 확인하며, 이전 마스킹 완료 표시만으로 허가하지 않는다.
- 휴대폰에서 복호화된 뒤의 복사·화면 캡처, 오프라인 상태에서의 즉시 철회 한계를 명시한다.
- 검증 또는 AI 장애로 반출이 보류되더라도 암호화와 접근통제를 해제하는 우회 경로를 만들지 않는다.

## 11. 평가 데이터와 AI 기여도 검증

### 11.1 데이터 구성

합성 환자정보와 사용권·개인정보 상태를 검증한 자료를 사용하여 다음 평가 집합을 제안하라.

- 한국어 판독문·진료 의뢰서·문진 메모.
- 한국어·영어 혼용, 한자·영문 이름, 보호자·의료진 이름, 동명이인.
- 띄어쓰기·줄바꿈·오탈자·OCR 오류·숫자 분리.
- 주민등록번호 형태, 병원 환자번호·접수번호, 연락처·주소·이메일.
- 날짜가 생년월일인지 검사일인지 문맥으로 구별해야 하는 사례.
- 인명처럼 보이는 의학용어·약물명·기관명 등 오탐 유발 사례.
- 개인정보가 전혀 없는 정상 문서.
- 합성 식별정보를 삽입한 DICOM 태그, 중첩 Sequence, 영상 글자와 복수 프레임.
- 글자는 없어도 외형·임상 조합으로 재식별 위험이 남는 사례.
- 손상 파일, 미지원 파일, 입력 길이 초과, 작업 중 권한 철회 사례.

공개 의료문서나 다운로드 가능한 DICOM이라고 해서 개인정보가 없는 것으로 가정하지 않는다. 학습·검증·최종 평가 자료를 분리하고, 같은 환자·기관 양식·템플릿 변형이 양쪽에 섞여 결과를 부풀리지 않게 한다.

### 11.2 비교 실험

동일한 평가 집합에서 다음을 비교하라.

| 방식 | 확인할 기여 |
| --- | --- |
| 규칙 단독 | 명확한 식별자 탐지의 기준 성능과 문맥 한계 |
| Privacy Filter 단독 | 문맥 기반 탐지와 한국어·병원 식별자 취약점 |
| 규칙 + Privacy Filter + 정책 | 추가 탐지, 오탐·미탐 변화, 임상정보 보존, 처리 비용 |

최종 결합 방식의 효과를 주장할 때 모델 추가 효과와 정책 변경 효과를 가능한 한 분리한다.

평가 지표:

- 유형별 Precision·Recall·F1과 정확한 구간 일치 여부.
- 문서별 잔존 개인정보 비율과 불필요한 반출 허용 건수.
- 직접 식별자·병원 식별자·한국어 이름 각각의 미탐지 수.
- 임상정보의 불필요한 삭제·변경과 중요 표현 보존.
- 픽셀 처리의 대상 프레임 포함률, 남은 식별정보와 해부학적 영역 손상.
- DICOM 재파싱, 필수 속성, UID 참조, 뷰어 조회 가능 여부.
- 마스킹 없는 태그 처리 경로의 불필요한 픽셀 변경 여부.
- p50/p95 지연, 최대 메모리, 동시 요청 처리량, timeout.
- 장애·권한 변경·미지원 입력에서 금지된 원본 반출이 발생했는지.
- 로그·오류·검토 화면 밖에서 개인정보가 노출되었는지.

**목표값·측정값·공개 벤치마크를 구별**하라. 실제 평가를 하지 않았다면 결과를 `미측정`으로 표시한다. 합성 시험에서 누출 0건이 관찰되더라도 전체 의료환경에서 누출이 없다고 보증하지 않는다. 분모·실패 수·입력 분포와 일반화 한계를 함께 적는다.

## 12. 법적·운영적 적용 검토

법률 적합 여부를 AI 탐지 결과로 판정하지 않는다. 아래 항목의 해당 여부와 필요한 근거를 실행일 기준 공식 원문에서 확인하라.

- 개인정보·민감정보·고유식별정보의 처리 근거.
- 진료 목적 제공과 연구·교육·데모·AI 이용의 목적 차이.
- 가명처리 후에도 남는 의무와 재식별·결합 위험.
- 제3자 제공, 처리 위탁, 국외이전이 발생하는지.
- 보관·파기, 환자 가명 매핑, 접근권한, 감사정보의 관리.
- 의료법상 기록 열람·사본 제공·진료정보 전달에 관련된 요건.
- 적용하려는 보건의료 데이터 활용 지침의 현행 판본과 적용 범위.

원문 확인 출발점: [국가법령정보센터 개인정보 보호법](https://law.go.kr/LSW/lsInfoP.do?lsId=011357).

확인한 조문·시행일·문서명·링크를 제시하라. 확인이 부족한 부분은 **“최신성 확인 필요” 또는 “출처 확인 한계 있음”**으로 표시한다. 마스킹, DICOM 프로파일 적용, 사람의 승인이 곧 익명화·적법성 보장·인증 취득을 의미한다고 표현하지 않는다.

## 13. MVP 범위와 구현 순서

초기 기본안은 **텍스트 탐지 + 한국어 식별자 규칙 + 목적별 정책 + 반출용 처리 사본 + 감사 + 정량 평가**로 두고 타당성을 판단하라.

다음 단계를 현재 저장소와 일정에 맞게 조정한다.

| 단계 | 작업 | 완료 증거 |
| --- | --- | --- |
| 0 | 기존 데이터 흐름·권한·원문 노출 위치·장비 확인 | 구현/계획/미확인 구분표, 연결 지점 |
| 1 | 로컬 Privacy Filter와 규칙의 텍스트 평가 | 한국어 사례별 오류와 실제 자원 사용량 |
| 2 | 목적별 정책·내부 API·반출 상태 연결 | 정상·실패·권한 변경 시나리오 증거 |
| 3 | 지원 범위를 제한한 DICOM 태그 처리 | 참조 무결성·뷰어 조회·원본 보존 확인 |
| 4 | 전체 흐름과 비교 평가·시연 정리 | AI 추가 효과, 실패 처리, 재현 가능한 결과 |
| 확장 | OCR·픽셀 처리·복수 프레임·한국어 파인튜닝 | 별도 데이터·성능·품질 기준 충족 |

영상 개인정보 자동 제거를 시연에 포함해야 한다면, 4단계 이전에 **제한된 합성 영상 한 종류의 OCR·좌표·픽셀 처리 실증**을 넣고 추가 일정과 의존성을 제시한다. 제한된 성공을 전체 DICOM 지원으로 확대해 표현하지 않는다.

각 단계에 의존성·예상 노력·산출물·통과 조건을 붙인다. 일정이나 인력이 제공되지 않았다면 합리적 가정을 표시하여 계획을 완성한다. 반드시 필요한 질문만 마지막에 정리하고 그 질문 때문에 가능한 설계를 중단하지 않는다.

## 14. 최종 산출물 형식

설계 보고서는 아래 순서로 작성하라. 긴 문단보다 짧은 문장·글머리표를 사용하고 비교는 2열 또는 3열 표로 정리한다.

1. **도입 판단:** 적합성, 1차 적용 대상, 권고 배치, 우선 해결 과제를 먼저 제시한다.
2. **현황과 변경 범위:** 확인된 사실·설계 가정·미확인을 구별하고 기존 하이패스 흐름에 추가되는 지점을 표시한다.
3. **전체 구성도:** 제어 영역·영상 전달 영역·진료·반출 경로·신뢰 경계가 드러나는 한글 Mermaid 도식.
4. **상세 설계:** 데이터별 책임, 규칙과 AI 결합, 정책표, DICOM·픽셀·QR·모바일 처리.
5. **인터페이스 계약:** 내부 API, 요청·응답 예시, 상태 전이, 오류, 권한·버전·사본 연결.
6. **검증 계획과 시연:** 비교 실험, 지표, 합격 기준의 근거, 정상·실패·경계 사례. 실행하지 않은 결과는 미측정으로 표시한다.
7. **구현계획:** MVP·확장 범위, 단계별 의존성·완료 기준·수정 대상 후보, 일정 가정.
8. **남은 결정과 근거:** 필요한 질문, 해결하지 못한 위험, 공식 출처와 확인일. 마지막에 첫 구현 단계에 사용할 실행 프롬프트 하나를 작성한다.

시연 시나리오는 최소한 다음을 포함하라.

- 정당한 진료 권한으로 정확한 환자의 영상을 조회하는 흐름.
- 개인정보가 포함된 합성 판독문을 목적에 맞게 처리하고 반출하는 흐름.
- 규칙만으로 놓친 문맥상의 식별정보를 AI가 보완하는 사례.
- 한국어 식별자와 임상 표현이 혼재한 경계 사례.
- 모델 장애·미지원 DICOM·검증 실패로 반출이 보류되는 흐름.
- 만료·재사용·수신처 변경된 티켓이 거부되는 흐름.

마지막 문장은 다음 취지로 작성하라.

> 하이패스에서 AI는 의료개인정보의 탐지를 보완하며, 실제 보존·처리·반출은 이용 목적과 권한에 따른 정책, DICOM 처리 검증, 필요한 검토 절차를 통해 결정한다.

이제 위 지시를 적용하여 **설계·구현계획서를 실제로 작성하라.** 모델 소개만 반복하거나 설계하겠다는 계획만 제시하지 않는다.
